# 자동화를 어디까지 행동하게 하는가

[ai-trust.md](ai-trust.md)가 **"AI의 출력을 믿을 수 있는가"**를 다룬다면,
이 문서는 **"자동화가 어디까지 행동해도 되는가"**를 다룹니다.
누가 무엇을 결정하고, 어디서 멈추며, 계열사(테넌트)마다 무엇이 분리되고, 기업 정보가 어디까지 나가는지입니다.

> **한 줄 요약**
> 자동화가 할 수 있는 행동은 **"한 서비스의 재기동" 하나**이고, 횟수·대상·계열사가 코드와 설정으로 묶여 있습니다.
> AI는 **행동 권한이 없습니다.** 분석과 설명만 하고, 그 결과는 사람에게 갑니다.

각 항목에는 **구현됨**(지금 코드에 있음)과 **설계**(도입 시 제시할 것)를 구분해 표시합니다.

---

## 1. 자동화의 행동 범위 (구현됨)

| 행동 | 주체 | 경계 | 근거 |
|---|---|---|---|
| 컨테이너 **재기동** | healer | 대상은 `pitwall_web` 뿐. socket-proxy가 허용하는 요청은 조회·로그·재기동 **3개**. 생성·삭제·exec·stop·kill은 불가 | [ADR-0001](adr/0001-docker-socket-access.md), [ADR-0002](adr/0002-remote-docker-access.md) |
| 재기동 **횟수** | healer | 대상별 **10분 3회** 초과 시 서킷 열림, 직전 재기동 후 **60초** 쿨다운 | `HEALER_MAX_RESTARTS` / `_WINDOW_SECONDS` / `_COOLDOWN_SECONDS` |
| 재기동 **결과 판정** | healer | **30초** 안에 healthy가 아니면 실패로 보고(Action Failed, Slack). 성공을 가장하지 않음 | `HEALER_VERIFY_TIMEOUT` |
| **사람 호출** | Zabbix | 문제가 **5분** 동안 해소되지 않으면 에스컬레이션 Slack | Action step 2 |
| 원인 **분석** | rca (AI) | **행동 권한 없음.** 결과는 Slack으로 사람에게만 감. 재기동 여부에 관여하지 않음 | [rca.md](rca.md) |
| 일일 **판정** | report (코드) | 판정은 코드 규칙, AI는 사유 설명만 | [ai-trust.md 원칙 5](ai-trust.md) |
| AI **호출량** | rca / report | 하루 20회 / 5회, 입력·출력 상한 | [ai-trust.md 원칙 6](ai-trust.md) |

**재기동으로 해결되지 않는 장애는 자동화가 끝까지 붙잡지 않습니다.** 의존 서비스 장애·설정 오류(5-B)에서
healer는 1회 재기동 후 실패를 보고했고, 무한 재기동 없이 5분 뒤 사람을 불렀습니다([chaos-scenarios.md](chaos-scenarios.md)).

## 2. 계열사(테넌트) 분리 (구현됨)

| 항목 | 내용 | 검증 |
|---|---|---|
| **활성화 게이트** | 계열사는 `HEALING_MODE_<회사>=off`로 시작. off면 감지만 하고 healer·RCA(외부 AI 호출)는 **0건**. 연결을 확인한 뒤 사람이 auto로 켬 | 2026-10-08, B를 켜기 전 event 151: 감지 O, Action 0건 |
| **서킷 분리** | 서킷 브레이커가 대상(`company/container`)별. A의 플래핑이 B의 복구를 막지 않음 | `test_healer_targets.py` |
| **라우팅 제한** | 목록에 없는 `(company, container)`는 healer가 403 | 〃 |
| **네트워크 격리** | 각 VM의 2375는 mon의 보안 그룹만 허용. VM-A ↔ VM-B는 서로 닿지 않음 | ADR-0002 검증 #9 (타임아웃) |
| **실행 격리** | A 장애 중 B·mon의 컨테이너는 재기동되지 않음 | 5-A / 5-B, `StartedAt` 불변 |

## 3. 계열사별 복구 정책 (설계)

**지금**: `MAX_RESTARTS`·쿨다운·검증 시간이 **전 계열사 공통**입니다. 서킷은 대상별이지만 **기준값은 하나**입니다.

**문제**: 계열사마다 서비스 성격이 다릅니다. 예를 들어 재기동이 비싼 서비스(세션 유실, 긴 워밍업)는
더 적게·더 천천히 재기동해야 하고, 무상태 서비스는 더 적극적으로 재기동해도 됩니다.

**설계안**: `HEAL_TARGETS`의 각 대상에 정책을 선택적으로 둡니다. 없으면 전역값을 씁니다.

```json
[{"company": "A", "container": "pitwall_web", "proxy": "<VM-A>:2375",
  "policy": {"max_restarts": 2, "window_seconds": 1800, "cooldown_seconds": 300, "verify_timeout": 60}},
 {"company": "B", "container": "pitwall_web", "proxy": "<VM-B>:2375"}]
```

- 정책은 **값만** 바꿀 수 있고, 행동의 종류(재기동 외의 조치)는 늘리지 않습니다.
- 정책 변경은 mon의 설정 변경이므로 기존 배포 절차(커밋 → 서버 `git pull` → 재기동)를 그대로 거칩니다.
- 4절의 **계열사별 AI 전송 차단**도 같은 자리(`policy.ai_analysis`)에 두면 계열사 정책이 한 곳에 모입니다.

## 4. 외부 AI로 기업 정보가 나가는 문제 (피드백 ④)

AI 분석은 OpenAI API로 나갑니다. **무엇이, 얼마나, 어떤 형태로** 나가는지를 줄이는 것은 구현했고,
**계약·법·조직 차원의 통제**는 도입 시 설계로 제시합니다.

### 구현한 것 vs 도입 시 설계로 제시할 것

| 구분 | 항목 | 내용 | 위치 / 근거 |
|---|---|---|---|
| **구현** | **로그 압축** | 같은 패턴은 최신 N건만, 길이 상한 12,000자. 로그의 약 96%가 헬스체크 줄이라 **보내는 양 자체를 줄임**. 5-B 실측: 170줄 / 15,297자 → **25줄 / 2,252자** | `automation/rca/compress.py`, [rca.md](rca.md) |
| **구현** | **마스킹** | 경계를 넘는 모든 본문은 `redact()`를 통과(불변식). IP·내부 호스트명·이메일·전화·주민번호·카드번호·AWS 식별자·비밀값을 가림. IP·호스트명은 **호출 단위 가명**(`<ip-1>`)으로 바꿔 분석력은 유지 | `automation/common/redact.py` |
| **구현** | **집계값 전송** | 일일 보고서는 **원시 로그를 보내지 않고** 집계 JSON(최대 16,000자)만 보냄 | [daily-report.md](daily-report.md) |
| **구현** | **판정 코드화** | 판정은 코드가 정하고 AI는 설명만 함. 그래서 **AI를 끄거나 막아도 판정과 보고서는 그대로 나옴** → 전송 차단이 기능 상실로 이어지지 않음 | [ai-trust.md 원칙 5](ai-trust.md) |
| **구현** | **제공자 교체 가능 구조** | 외부 AI 호출은 `common/llm.py`의 `analyze()` **한 곳**뿐. rca·report는 이 함수만 부름. 제공자를 바꾸려면 **이 파일의 구현만** 교체하면 됨 (설정만으로 바뀌는 구조는 아님) | `automation/common/llm.py` |
| 설계 | **법적 검토 쟁점** | 아래 "법적 검토 쟁점" | — |
| 설계 | **OpenAI 기업 계약 옵션** | 무보관(Zero Data Retention), 데이터 저장 지역(국내 저장 가능 여부), 학습 미사용 확인 | 아래 |
| 설계 | **사내 모델 전환 경로** | `llm.py` 교체 → 사내 추론 서버. 전환 기준과 회귀 검증 | 아래 |
| 설계 | **계열사별 전송 차단** | 계열사 정책으로 AI 분석을 끄면, 그 계열사 데이터는 외부로 한 줄도 나가지 않음 | 아래 |

### 법적 검토 쟁점 (설계)

법률 자문이 아니라, 도입 전에 **법무 검토를 요청할 항목**의 목록입니다.

- **개인정보의 국외 이전**: 로그에 개인정보가 섞일 수 있습니다(접속 IP, 이메일 등). 마스킹 후에도 남는 정보가
  개인정보에 해당하는지, 해당한다면 국외 이전 요건(개인정보 보호법)을 어떻게 충족할지.
- **처리 위탁인가, 제3자 제공인가**: 외부 AI 제공자에게 보내는 것의 법적 성격과, 그에 따른 고지·동의·계약 요건.
- **계열사 간 정보 흐름**: mon(지주/운영 주체)이 계열사의 로그를 모아 외부로 보내는 구조의 근거와 계약.
- **업종별 규제**: 금융·의료 등 계열사 업종에 따른 추가 제한(망 분리, 국외 반출 제한 등).
- **영업비밀·비밀유지 의무**: 고객사와의 계약상 외부 반출이 금지된 정보가 로그에 포함될 가능성.

### OpenAI 기업 계약 옵션 (설계)

계약 시 **확인하고 문서로 받을 것**입니다. 정책은 바뀔 수 있으므로 공개 문서가 아니라 계약서 기준으로 판단합니다.

| 옵션 | 확인할 것 |
|---|---|
| **무보관 (Zero Data Retention)** | 요청·응답이 남용 모니터링 목적으로도 저장되지 않는지, 적용 대상 엔드포인트(현재 사용하는 Responses API 포함 여부) |
| **데이터 저장 지역** | 국내(한국) 저장·처리 옵션의 제공 여부와 조건 |
| **학습 미사용** | API 데이터를 모델 학습에 쓰지 않는다는 조항이 계약에 명시되는지 |

### 사내 모델 전환 경로 (설계)

1. **교체 지점은 하나**: `llm.analyze()`의 구현을 사내 추론 서버 호출로 바꿉니다. rca·report 코드는 그대로입니다.
2. **전제 조건**: 사내 모델이 **JSON 스키마(strict) 출력**을 지원해야 합니다. 지금 근거 대조(ai-trust 원칙 2)와 판정 분리가 구조화 출력에 기대고 있습니다.
3. **회귀 검증**: 5-B의 장애 시나리오(의존 서비스·설정 오류 × 계열사)를 **분류 정확도 회귀 세트**로 씁니다.
   현재 OpenAI 기준 4/4 정답, 근거 원문 일치 100%입니다. 사내 모델이 이 기준을 넘는지 확인한 뒤 전환합니다.
4. **단계적 전환**: 계열사별 정책(3절)으로 민감한 계열사부터 사내 모델로 보내고, 나머지는 기존 경로를 유지할 수 있습니다.

### 계열사별 전송 차단 (설계)

- **연결 지점은 이미 있습니다**: healer가 rca로 넘기는 작업(`/analyze`)에는 `company`가 이미 들어 있습니다. 지금 rca는 이 값을 쓰지 않습니다.
- **설계안**: 계열사 정책 `policy.ai_analysis = "off"`이면 rca는 외부 호출 없이 **"AI 분석 생략(계열사 정책)"**만 기록하고 Slack에 알립니다.
  재기동·판정·에스컬레이션은 1절대로 동작합니다(판정 코드화 덕분).
- 일일 보고서도 같은 정책으로 해당 계열사의 집계를 AI 입력에서 제외합니다.
- `HEALING_MODE`(재기동 여부)와 **별개 스위치**로 둡니다. "자동 복구는 켜되 외부 AI는 쓰지 않는다"가 가능해야 합니다.

## 면접·발표용 요약

- **자동화는 무엇까지 하나?** 한 서비스의 재기동까지. 횟수 제한(10분 3회)·결과 검증(30초)·실패 시 사람 호출(5분)이 코드로 묶여 있습니다.
- **AI는 무엇까지 하나?** 분석과 설명만. 재기동도 판정도 결정하지 않습니다.
- **계열사가 늘면?** 대상별 서킷·라우팅 제한·보안 그룹으로 서로 영향을 주지 않고, 새 계열사는 off로 시작합니다.
- **기업 정보가 외부 AI로 나가는 문제는?** 보내는 양을 줄이고(압축·집계), 가리고(마스킹), 없어도 돌아가게(판정 코드화) 했고,
  제공자 교체 지점을 한 곳으로 모았습니다. 계약·법·사내 모델·계열사별 차단은 도입 시 위 설계로 제시합니다.
